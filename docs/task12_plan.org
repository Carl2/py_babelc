* Goal

  Prove that ~py_babelc --type ipc~ produces *semantically identical* output to
  ~babelc -babelcOutput=Ipc~ for a representative corpus of real production
  headers.  This is critical because this is production code that will be
  generated and deployed across 50+ services.

* Strategy

  1. Fix known semantic bugs discovered during initial output comparison.
  2. Establish a normalisation procedure that removes *expected* differences
     (C++17 guards, file paths) while preserving all semantically meaningful
     differences.
  3. Collect a corpus of 7 production headers (varying complexity) with their
     committed babelc-generated ~.ipc.h~ reference output.
  4. Run ~py_babelc~ on each header, normalise both outputs, and assert the
     diff is empty.

* Known Bugs to Fix

** Bug 1+3: Guard macro double-underscore (templates)

   *Symptom:* py_babelc emits ~__HAVE__ADDRESSBOOK__V1__SEX_IPC_DECLARATIONS__~
   and ~__HAVE_BABEL__IPC__ADDRESSBOOK__V1__...__~ while babelc emits
   ~__HAVE___ADDRESSBOOK__V1__SEX_DECLARATIONS__~ and
   ~__HAVE_BABEL__IPC____ADDRESSBOOK__V1__...__~ (extra ~__~ from ~::~ prefix).

   *Root cause:* The ~_guard_macro~ filter receives ~addressbook::v1::Sex~
   (without leading ~::~).  babelc always uses the fully-qualified name with
   leading ~::~ (e.g. ~::addressbook::v1::Sex~) → ~__ADDRESSBOOK__V1__SEX~
   with a leading ~__~ that produces the double-underscore pattern.

   *Fix:* In all templates (~struct.j2~, ~container.j2~, ~enum.j2~,
   ~interface.j2~), replace ~{{ X.qualified_name|guard_macro }}~ with
   ~{{ ("::" + X.qualified_name)|guard_macro }}~ so the leading ~::~ is
   always present before the guard transform.

** Bug 2: ~_TupleView~ container field type

   *Symptom:* In the struct ~Person_TupleView~, py_babelc emits
   ~::addressbook::v1::PhoneNumbers_ArrayView<Boolean,IpcPolicy>~ for the
   container-typed field, while babelc emits ~::addressbook::v1::PhoneNumbers~
   (the raw alias name).

   *Root cause:* The ~ipc_template_type~ function resolves alias-typed fields
   to their ~_ArrayView~ form.  But babelc only uses ~_ArrayView~ in the
   *container declaration*, not in the struct's ~_TupleView~.  For
   ~_TupleView~ fields that are containers, babelc uses the undecorated
   qualified type name.

   *Fix:* In ~_enrich_field~, when computing ~wire_type~ for a
   container-typed field within a struct's ~_TupleView~, use the raw qualified
   name of the container alias, not the ~_ArrayView~ template type.

** Bug A: ~const~ prefix in parameter type resolution

   *Symptom:* py_babelc emits ~::const Person~ instead of
   ~::addressbook::v1::Person~ in interface proxy method signatures.  This
   cascades to break type lookups, ~_is_complicated_field~, read_block
   generation, vtable signatures, and parameter initializers.

   *Root cause:* In ~clang_parser.py:_extract_parameters~, when a parameter
   is passed as ~const Person &~, libclang's ~pointee.spelling~ returns
   ~"const Person"~.  The ~_resolve_type_spelling~ function strips leading
   ~::~ but does not strip the ~const ~ prefix.  The resulting
   ~type_name="const Person"~ then fails to resolve against the type model
   (which stores ~"Person"~ or ~"addressbook::v1::Person"~).

   *Fix:* In ~_extract_parameters~, after computing ~type_spelling~ for a
   ref parameter (where ~is_const=True~), strip any leading ~"const "~ prefix
   from ~type_spelling~ since the constness is already captured in ~is_const~.

** Bug B: ~vtable_signature~ logic broken for multiple params

   *Symptom:* The ~.template addMethod< ... >~ call emits wrong types.
   Special-case logic only handles the first param and fails to produce
   correct comma-separated ~ipc_template_type~ for all params.

   *Expected:* ~addMethod< RetType, Arg1IpcType, Arg2IpcType, ... >~
   For void-returning methods with args: ~addMethod< void, ArgTypes... >~
   For non-void with no args: ~addMethod< RetIpcType, void >~

   *Fix:* Rewrite ~_vtable_signature~ to:
   1. Map return type via ~ipc_template_type~ (or ~"void"~).
   2. Map each param via ~ipc_template_type~.
   3. Join with ~", "~.
   Pattern: ~"RetIpcType, Arg1IpcType, Arg2IpcType"~ or ~"void, ArgTypes"~ or
   ~"RetIpcType, void"~ for no-args non-void.

** Bug C: ~vtable_signal_signature~ includes ~void~ return

   *Symptom:* Signal vtable entries emit ~addSignal< void, ArgType >~ but
   babelc emits ~addSignal< ArgType >~ (no return type prefix for signals).

   *Fix:* Create a separate ~_vtable_signal_signature~ that emits only the
   parameter types (no return type).  Pattern: ~"Arg1IpcType, Arg2IpcType"~
   or just ~"ArgIpcType"~ for single-param signals.

** Bug D: Non-void return blocks unimplemented

   *Symptom:* ~write_return_block~ and ~client_read_return_block~ in
   ~EnrichedMethod~ are always ~""~.  Methods with non-void returns
   (e.g. ~getActiveClass() → ConnectionClass~, ~getCommInfo() → std::string~)
   produce broken output.

   *Required for:* ~bos_connection.h~ (enum return), ~comminfo_cli.h~
   (string return).

   *Fix:* Implement in ~ipc_generator.py:_enrich_method~:

   - ~write_return_block~ (ImplementationProxy static handler): Serialize
     the return value into ~theReturnValue~ message:
     #+begin_src c++
     IpcPolicy::appendMessageArguments(
         theReturnValue,
         <write_expr>(theProxy.methodName(args...))
     );
     #+end_src
     Where ~<write_expr>~ is ~.c_str()~ for string, ~static_cast<underlying>~
     for enum, direct for builtin.

   - ~client_read_return_block~ (ClientProxy): Declare local return var,
     deserialize from reply, return:
     #+begin_src c++
     auto theMessageReturnValue = itsIpcPolicy->sendMessage( theIpcMessage );
     IpcPolicy::getMessageArguments(
         theMessageReturnValue,
         <read_ref>(theIpcReturnValue)
     );
     return theIpcReturnValue;
     #+end_src

   Also update ~interface.j2~ to render the non-void ClientProxy pattern:
   - Declare ~RetType theIpcReturnValue;~ before creating message
   - Use ~auto theMessageReturnValue = itsIpcPolicy->sendMessage(...)~
   - Render ~client_read_return_block~ after send

** Bug E: Struct complicated field indentation + missing semicolon

   *Symptom:* The ~IpcReadContainer~ / ~IpcWriteContainer~ calls for
   complicated struct fields use 16-space indentation and are missing the
   trailing ~;~.  babelc uses 12-space indent with ~);~ at the end.

   *Fix:* In ~_read_expr_for_field~ and ~_write_expr_for_field~, change the
   indentation of complicated field expressions from 16sp/12sp to 8sp/12sp
   (matching the surrounding template indent) and ensure the closing ~)~ has
   a ~;~ appended.

** Bug F: ~{}~ initializer on complicated params

   *Symptom:* py_babelc emits ~::addressbook::v1::Person thePerson{};~ but
   babelc emits ~::addressbook::v1::Person thePerson;~ (no value-init braces
   for complicated types like structs/containers).

   *Fix:* In ~_enrich_param~, set ~initializer = ""~ when
   ~_is_complicated_field(type_name, cu)~ is True.

* Normalisation Procedure

  When comparing py_babelc output against babelc reference, the following
  transformations are applied to *both* files before diffing:

  1. *Include guard name* — replace the top-level ~#ifndef __XXX__~ / ~#define __XXX__~
     with a fixed placeholder (these are derived from the output file path, which
     always differs).

  2. *Original header include path* — replace ~#include "/path/to/header.h"~ with
     ~#include "HEADER"~.

  3. *C++17 compatibility guards* — remove all blocks of the form:
     #+begin_src text
     #if __cplusplus < 201700L
     namespace X { namespace Y {
     #else
     #+end_src
     and their corresponding:
     #+begin_src text
     #if __cplusplus < 201700L
     }}
     #else
     }
     #endif
     #+end_src
     Retaining only the C++20 variant (single ~namespace X::Y {~ and single ~}~).

  4. *Empty C++17 namespace blocks* — remove entire ~#if __cplusplus < 201700L~ /
     ~namespace babel { }~ / ~#else~ / ~namespace babel {~ / ~#endif~ blocks
     where the C++17 variant is effectively empty or identical to C++20.

  5. *Trailing whitespace* — strip all trailing spaces/tabs from each line.

  6. *Blank line normalisation* — collapse multiple consecutive blank lines to
     at most two.

  The normalisation is implemented as a Python function in the test module,
  making it auditable and deterministic.

      """Normalise generated output for semantic comparison."""
      lines = text.splitlines()

                  j += 1

              continue

          # Skip standalone #endif that closes C++17 guard
          # (these follow the C++20 namespace close)

* Implementation Notes

** Why not byte-identical comparison?

   py_babelc deliberately targets C++20-only output.  The original babelc
   emits C++17 fallback code (~#if __cplusplus < 201700L~) which adds ~133
   lines to the ~addressbook.ipc.h~ output (908 vs 775 lines).  Since all
   target platforms are C++20, this fallback code is dead weight.

   The normalisation procedure strips these guards from the babelc reference
   so we can compare the semantic content.

** Source of truth

   The committed ~gen_files/*.ipc.h~ in production repos are the canonical
   reference — they were generated by babelc at specific SDK versions and
   are used in CI builds.  We compare against these, not against
   freshly-generated babelc output (which would require the exact SDK version
   and sysroot).

** Include path in generated output

   babelc embeds the absolute path of the source header in the ~#include~
   directive.  py_babelc does the same (using the path passed on the command
   line).  Since these always differ between test runs, we normalise them away.

** Variant types (~registered_services.h~)

   This header uses ~std::variant~ — which exercises the ~VariantType~ path
   in the type model and may require additional template logic not yet
   implemented.  This header is excluded from the automated corpus and will
   be handled in a follow-up task if variant IPC support is needed.

** Signal vtable pattern

   Signals never have a return type.  The ~addSignal~ template takes only the
   argument types (using ~ipc_template_type~ mapping):
   - ~addSignal< std::uint8_t >( "method", ... )~ — single enum param
   - ~addSignal< const char *, std::uint64_t, ::ns::Payload, Boolean >~ — multi-param
