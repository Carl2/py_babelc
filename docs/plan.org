* Overview

  Replace the C++ babelc tool with a Python package (~py_babelc~) that uses
  libclang to parse annotated C++ headers and generates sdbus D-Bus IPC stubs
  (server) and proxies (client) using Jinja2 templates.

  The existing ~sdbus-policy.h~ runtime header is *not* changed — the generated
  code continues to depend on it.

  All Python code follows a functional, railway-oriented style using the
  ~pymonad~ library's ~Maybe~ monad, curried functions, and bind-pipelines.

* Goals

  - Parse annotated C++ headers correctly using a real C++ AST (libclang).
  - Generate the same sdbus IPC stub/proxy code that babelc currently generates.
  - Generate the same JSON serialization/deserialization code that babelc
    currently generates (~-babelcOutput=Json~ mode) — used by 22 repos.
  - Keep existing header annotation syntax (~[[babelc::ipc_type(...)]]~ etc.)
    intact — no changes required to consumer headers.
  - Write all Python in functional railway-oriented style (pymonad/Maybe).
  - Ship as an installable Python package with a clean CLI (~pyproject.toml~).
  - Include a test suite (pytest) covering parsing, type model, and generation.

* Non-Goals

  - Stream serialization generator.
  - Dependency file generator.
  - Drop-in CLI compatibility with babelc's option syntax.
  - Replacing or modifying ~sdbus-policy.h~.

* Constraints & Assumptions

  - libclang Python bindings (~clang~ package) available in the build environment.
  - ~pymonad~ available via pip.
  - ~jinja2~ available via pip.
  - Python >= 3.10 (dataclasses, match statements, ~|~ union types).
  - Consumer headers use ~[[babelc::*]]~ attribute syntax (GCC C++20+).
  - A ~libclang.so~ shared library is present on the build host.
  - Reference babelc binary is at
    ~/opt/sspc/0.24.1/sysroots/x86_64-wrlinuxsdk-linux/usr/bin/babelc~.

* Risks & Open Questions

  1. *Attribute visibility in libclang*: ~[[babelc::ipc_type(...)]]~ is a vendor
     attribute unknown to Clang. A lightweight regex pre-pass rewrites these to
     ~[[clang::annotate("babelc::X=Y")]]~ before feeding to libclang, so they
     appear as ~AnnotateAttr~ nodes in the AST.
     - Risk: edge-case attribute syntax (nested parens, multiple args) needs
       careful regex handling. Mitigate with targeted unit tests.

  2. *libclang version compatibility*: Different libclang versions expose slightly
     different APIs. Pin the ~clang~ package version in ~requirements.txt~ and
     document the minimum supported version.

  3. *Template completeness*: The babelc IPC generator produces ~908 lines for a
     simple interface (~addressbook.h~). Generated patterns include: enum
     validation, struct serialization (TupleView, ReadContainer, WriteContainer),
     varying-length container serialization, implementation proxy, client proxy,
     client proxy wrapper, broadcast listener, broadcast proxy, registration
     functions. Each must be ported to Jinja2 templates.

  4. *Cross-compilation context*: The tool runs on the build host. libclang must
     parse headers referencing target-platform standard library headers. May need
     ~--sysroot~ or ~-I~ flags passed through to libclang.

  5. *JSON generator self-containment*: Each ~.json.h~ embeds the entire
     ~babel::JSON::parser~ (~735 lines) plus generic templates for arithmetic,
     string, bool, containers, optionals, variants, and pointers.  Our Jinja2
     output must reproduce this self-contained structure exactly because
     consumers ~#include~ the generated header directly without linking a
     separate library (except the optional ~babelc_json_helpers~ convenience
     layer in ~lib-ocpcommon~).

* Generated Output Structure

  For each input header, the generated ~.ipc.h~ follows this structure
  (derived from reference output of ~addressbook.h~):

  1. Include guard
  2. Standard includes (~<memory>~, ~<type_traits>~, ~<algorithm>~, ~<tuple>~, ~<array>~)
  3. Include of original header
  4. *Forward declarations* (per interface):
     - ~registerXxxImplementation()~
     - ~lookupXxxImplementation()~
     - ~registerXxxBroadcastListener()~ (if all methods are void-returning)
     - ~getXxxBroadcastProxy()~ (if all methods are void-returning)
  5. *babel:: type trait helpers* (once, guarded):
     - ~is_supported_ptr~, ~is_supported_container~, etc.
     - Container specializations (~std::vector~, etc.)
  6. *babel::ipc helper templates* (once, guarded):
     - ~ArrayValue~, ~BooleanReference~, ~EnumReference~, ~StringReference~
     - ~ArrayReference~, ~EnumArrayReference~, ~MakeArrayReference~ variants
  7. *Per-type IPC declarations* (each guarded):
     - For containers (vector/list): ~_ArrayView~ typedef, ~IpcReadContainer~/~IpcWriteContainer~ decls
     - For enums: ~IpcEnumValidate~ decl
     - For structs: ~_TupleView~ typedef, ~IpcReadContainer~/~IpcWriteContainer~ decls
  8. *Per-type IPC implementations* (each guarded):
     - Container read/write bodies
     - Enum validate switch-case body
     - Struct read/write bodies (composing field-level read/write calls)
  9. *Per-interface stubs* (guarded):
     - ~XxxImplementationProxy~ — server-side, inherits interface + Implementor
     - ~XxxClientProxy~ — client-side, creates messages and sends
     - ~XxxClientProxyWrapper~ — wraps client with local shortcut
     - ~XxxBroadcastListener~ — signal receiver (if applicable)
     - ~XxxBroadcastProxy~ — signal emitter (if applicable)
  10. *Per-interface registration implementations* (guarded):
      - ~registerXxxImplementation()~ — creates proxy, builds vtable, publishes
      - ~lookupXxxImplementation()~ — creates client proxy wrapper, registers client
      - ~registerXxxBroadcastListener()~ — creates listener, builds signal vtable
      - ~getXxxBroadcastProxy()~ — creates broadcast proxy
  11. Final ~#endif~

* JSON Generator — Background

  The babelc JSON generator (~-babelcOutput=Json~) is used by 22 repos in the
  release.  It produces a self-contained ~.json.h~ header that can be
  ~#include~-d to get JSON serialization/deserialization for annotated types.

** What it generates

   Each ~.json.h~ file contains (in order):

   1. Include guard + standard includes (~<memory>~, ~<type_traits>~, ~<ostream>~,
      ~<sstream>~, ~<cctype>~)
   2. Include of the original header
   3. The full ~babel::JSON::parser~ namespace (~735 lines) — a complete JSON
      parser with ~Value~ hierarchy (~String~, ~Number~, ~Object~, ~Array~,
      ~Boolean~, ~Null~), stream tokenization, character traits, error reporting
   4. ~babel::JSON::Indent~ class for pretty-printing
   5. ~babel::~ type trait helpers (~is_supported_container~ etc.) — same as IPC
   6. Forward declarations for all ~babel::JSON~ generic templates
   7. Per-type code in the user's namespace:
      - For structs: ~interpretJSON<CharT>(Value, Struct&)~ + ~writeJSON<CharT>(ostream, Struct, Indent)~
      - For enums: string↔enum lookup or numeric cast
   8. Full implementations of all ~babel::JSON~ generic templates

** Key differences from IPC generator

   | Aspect                 | IPC                                     | JSON                                      |
   |------------------------+-----------------------------------------+-------------------------------------------|
   | Output suffix          | ~.ipc.h~                                | ~.json.h~                                 |
   | Interfaces handled     | Yes (proxy classes, registration fns)   | No — interfaces are excluded              |
   | Embedded runtime       | No (depends on ~sdbus-policy.h~)        | Yes (~babel::JSON::parser~ embedded)      |
   | Serialization target   | D-Bus messages (~IpcPolicy~ template)   | JSON text (~ostream~ / ~Value~ tree)      |
   | Per-struct pattern     | TupleView + IpcRead/WriteContainer      | interpretJSON + writeJSON                 |
   | Per-enum pattern       | IpcEnumValidate (switch-case)           | String↔enum lookup table (or numeric)     |
   | Variant support        | Via ~IpcPolicy::VariantType~            | JSON type dispatch + sanity checks        |
   | Optional support       | ~std::array<wire_type, 1>~              | JSON null + inner type                    |
   | Field classification   | Simple vs complicated (batched)         | Required vs optional (has default value)  |

** Runtime helper library (~lib-ocpcommon~)

   ~babelc_json_helpers.h~ / ~babelc_json_helpers.cpp~ provide a convenience
   layer on top of the generated code:
   - ~RootObject~ — wraps a parsed JSON ~Object~
   - ~getRootObject(json_string)~ — parses JSON text, returns root object
   - ~parseElement<T>(element)~ — calls ~babel::JSON::interpretJSON<char>~
   - ~parseRootObjectElement<T>(json, name)~ — one-shot parse of a named element
   This library is *not generated* — it's hand-written code that depends on the
   generated ~.json.h~ headers.
